    After:

          # Full check_vpn_health runs at loop top; this only cuts sleep short
          # when local state is definitively dead (process gone, socket closed).
          _dg_elapsed=0

          wait "$storm_sleep_pid" || true
          storm_sleep_pid=""

  <action>
    REC-04: Require FAILBACK_THRESHOLD (3) consecutive healthy checks before
    transitioning from DEGRADED back to normal.  Prevents oscillation where
    one OK check resets fail_count, then the next check fails again.

    1. Add constant near L35 (after DEGRADED_INTERVAL):
       FAILBACK_THRESHOLD=3

    2. Add global counter near L3830 (existing counter init block):
       _healthy_consecutive=0

    3. Modify the health=OK branch (L4045-4063):
       Currently: immediately sets fail_count=0, reconnect_count=0, etc.
       Change to:

       elif [ "$health" = "OK" ] || \
            { ! _health_is_failure "$health" && [ -n "$health" ]; }; then
           # Exit country enforcement BEFORE failback gate -- a blocked exit
           # is NOT a healthy check and must not accumulate toward the gate.
           # Placing this inside the gate would cause a reconnect loop:
           # fail_count=$FAIL_THRESHOLD stays set, gate never clears it,
           # reconnect trigger fires every cycle. (Kimi R1 #1)
           if [ "$_exit_country_blocked" -eq 1 ]; then
               _exit_country_blocked=0
               _healthy_consecutive=0
               fail_count=$FAIL_THRESHOLD
               log "Exit country enforcement: non-allowed exit, forcing reconnect"
           else
               _healthy_consecutive=$((_healthy_consecutive + 1))
               if [ "$_healthy_consecutive" -ge "$FAILBACK_THRESHOLD" ] || \
                  { [ "${fail_count:-0}" -eq 0 ] && [ "${transient_count:-0}" -eq 0 ]; }; then
                   # Fully healthy or was never degraded -- reset all counters
                   fail_count=0
                   reconnect_count=0
                   transient_count=0
                   _cn_consecutive=0
                   _transit_grace_ts=0
                   _healthy_consecutive=0
               fi
           fi
           # ... rest of OK block (backoff reset, etc.) unchanged

    The second condition (fail_count==0 && transient_count==0) is the
    "already normal" fast-path: when not degraded, the gate is a no-op.
    The gate only delays counter reset when transitioning FROM degraded.

    4. Reset _healthy_consecutive=0 in all non-OK branches so a single
       failure restarts the gate count.  Exhaustive list of branches:
       - LOCAL_FAIL (L4002): fail_count=$FAIL_THRESHOLD
       - TCP_BLOCK/control_probe success (L4020): fail_count=$FAIL_THRESHOLD
       - TCP_BLOCK/control_probe fail (L4028): transient_count++
       - PROXY_BROKEN (L4032): fail_count=$FAIL_THRESHOLD
       - CN (L4089): fail_count++ or _enter_storm_cooldown
       - else/transient (L4105): transient_count++
       Add _healthy_consecutive=0 in each of these 6 paths.

       Also reset _healthy_consecutive=0 in:
       - _enter_storm_cooldown (L1712-1718 counter reset block)
       - After connect_vpn returns in the reconnect trigger block (L4144+),
         so accumulated healthy checks from before reconnect do not carry
         over and prematurely pass the gate.
  </action>
