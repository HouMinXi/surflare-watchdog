<objective>
Fix procd respawn threshold exhaustion (SC4) by changing the retry limit
from 10 to 0 (infinite retries), and add a cron watchdog-of-watchdog
(OPS-02) as defense-in-depth so the watchdog is restarted even if procd
itself fails to respawn it.

Purpose: The post-v67 incident root cause was procd stopping respawns
after 10 rapid exits (instance-lock crash loop). retry=0 ensures procd
never gives up. The cron fallback covers procd-level failures.

Output: Modified init.d script with respawn 3600 5 0, and modified
install.sh with watchdog-of-watchdog cron entry.
</objective>

to:

The three parameters are: threshold=3600s (crash window), timeout=5s (restart delay), retry=0 (infinite retries). Per OpenWrt procd documentation and source (procd.sh _procd_add_array_data), retry=0 means procd never stops respawning the service.

Update the comment near this line (if one exists) or add a brief comment explaining: retry=0 enables infinite respawns so the watchdog always recovers from crash loops. The instance-lock fix (already deployed post-v67) prevents the rapid-exit pattern that originally triggered threshold exhaustion. The watchdog's internal rate limiting (storm cooldown, DEGRADED_INTERVAL) prevents connect storms during recovery.

Add a new variable near the DEADMAN_CRON definition (around line 226-230). The variable should be defined inside the procd guard block (if [ "$INIT" = "procd" ]):

In the crontab assembly block (lines 231-239):

The deadman cron (already deployed) removes the orphan killswitch but does NOT restart the watchdog -- this new cron fills that gap.
